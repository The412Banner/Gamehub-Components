GameHub Frame Gen Teardown

1.4.2 · old engine→ 1.4.8 · new engine, 2× only→ 1.4.9 · retrained, smaller

GameHub's frame generation doesn't live in the app. It ships inside the firmware, the Linux image the PC emulator runs on. Between firmware 1.4.2 and 1.4.9 upstream replaced the whole engine. The old one, built on Lossless Scaling's design, is gone. A new learned engine called GSFG took its place: first as a large model that could only double the frame rate (1.4.8), and a day later as a retrained, much smaller model that brought back 3× and 4× (1.4.9).

Background

How frame generation works

A game renders real frames. Frame generation invents extra frames in between so motion looks smoother. To do that it has to work out where every part of the picture moved between two real frames. That motion map is called optical flow. The engine then slides (warps) both real frames partway along the map and blends them into the new frame.

Every engine here searches coarse to fine. It looks at a tiny, blurry copy of the frame first to catch big moves cheaply, then refines on larger copies. Each copy is one level of a pyramid. The multiplier says how many frames you see per real frame: 2× means one invented frame between each pair.

Firmware ≤ 1.4.2

The old engine: LSFG's recipe, rebuilt

In plain words

A fixed recipe of GPU programs that searches for motion over 7 sizes of the picture, then paints the in-between frame. It came in two flavours, Performance and Quality, and could make 2, 3 or 4 frames per real frame.

  1. MipmapsShrink both frames into 7 sizes.mipmaps
  2. Feature passesPrepare images at each size, then a shared detail stack from the finest.alpha ×4 per size · beta ×5
  3. Motion, coarse → fineEstimate motion size by size, each level building on the last.gamma ×5 per size
  4. RefineExtra refinement on the 3 finest sizes.delta ×10 per size
  5. GenerateWarp and blend into the new frame.generate
  • Libraries: libGameScopeVK.so (2,219,144 B, sha256 c8f4809c…, the default, with direct rendering) and libGameScopeV2.so (the GPU-spoof variant).
  • Shaders: 54 GPU programs: two complete frame-gen sets (Performance and Quality) plus 3 texture decoders. Compiled with Google's glslc, debug names stripped.
  • Baked-in numbers: ≈28.9k fp16 constants inside the shaders (≈30.6k counting every weight slot).
  • Controls: a 9-byte control file written by the app: on/off, flow scale 0.2–1.0, model 0/1, multiplier 2–4.
  • Where it came from (our August 2026 finding): the design is derived from LSFG. It uses stage names that only lsfg-vk invented (delta0–9, gamma0–4, generate) and matches LSFG's shader wiring (12 of 13 layouts). It is not a byte copy (different compiler, 0% shared bytes), and its weights are its own, because LSFG has no learned weights to copy.

Firmware 1.4.8 · 2026-09-08

1.4.8: the engine is replaced

In plain words

GameHub deleted the old engine and shipped a new one, GSFG, which has learned what motion looks like instead of following a fixed recipe. This first version was big, but it could only ever make one in-between frame (2×).

  • libGameScopeVK.so is gone. libGameScopeV2.so (1,921,192 B) is now the only GameScope library, so direct rendering is gone for good. A new libsandboxfs-v2.so also appears; it has nothing to do with frame gen.
  • A new shader set: 65 GPU programs, 62 of them new, built with Khronos glslangValidator from GLSL with debug names left in (time, global_flow, local_flow…). Only the 3 texture decoders survive from the old engine.
  • 153 GPU passes per pair of real frames.
  • 2× is hard-coded. The one call into the interpolator passes a fixed time of 0.5 (exactly halfway), and the multiplier setting is never read. The frame pacer simply halves the frame interval.
  • The same control file, with a new meaning. The app still writes model and flow scale, but the engine converts them into a single "motion resolution" percentage. There is only one model now, so "Quality" no longer picks a different network.
Firmware 1.4.9 · 2026-09-09

1.4.9: retrained and slimmed

In plain words

A day later GameHub shipped a retrained GSFG about a third to a quarter of 1.4.8's size, with a coarser motion map, that can once again make up to three in-between frames (4×). It also benchmarks your GPU at startup to pick its fastest settings.

  • How multi-frame works: the app offers 2×, 3× and 4×. (The engine code itself clamps the setting to 2–6, so it would accept up to 6×, but the app doesn't offer it.) Motion is worked out once per pair of real frames, and only the final painting step is repeated for each in-between time (1/m, 2/m, … (m−1)/m).
  • How the tuner works: at startup it switches to 100% motion resolution and times shader work-group sizes. The default is 8×8; it tries 16×8, 8×16 and 16×16, measuring each 20 times. It keeps a candidate only if it's 2% faster on average and its slowest run beats the default's fastest. Nothing is saved, so it re-tunes every launch.
  • Formats: the engine's running state (encoder outputs and each level's context) is stored as 8-bit signed values, other working images as 16-bit float, and the final frame as normal 8-bit colour. Host and shaders agree, so this isn't a format bug.
Architecture · 1.4.9

Inside GSFG

The whole network was recovered from three tables inside the library: every working image (name, size, channels), every GPU pass in running order, and every shader. It's a learned optical-flow network in the PWC-Net family.

  1. EncoderLearns a compact description of each real frame; the same weights run on both frames.¼ · ⅛ · 1/16 size + 6 smaller · 42 passes
  2. Global motion searchFinds big movements, from a 1/512 copy up to ¼ size. At 7 of the 9 levels it compares a 7×7 neighbourhood in both directions.9 levels · 98-channel search · 53 passes
  3. Local motion searchA second guess tuned for small movements.⅛ → ¼ size · 11 passes
  4. SelectorDecides, pixel by pixel, which guess to trust.¼ size · 3 passes
  5. OutputSlides both real frames along both guesses and blends the 4 results at time t.full resolution · 1 pass per invented frame

The motion levels take the target time t as an input, and levels 9 to 3 reuse the same refine and update shaders (shared weights). The heavy 1×1 "combine" layers read their weights from buffers the host uploads at start-up; the rest have fp16 weights baked into the shader code.

Provenance

Is it a copy of LSFG?

In plain words

No. We re-ran the same tests that proved in August that the old engine was built on Lossless Scaling's design. They still fire on the old engine and come up empty on GSFG. GSFG is a different kind of engine, with its own trained weights.

What's still in common (coarse-to-fine motion, warping by time, blending two warped frames) is shared by all modern frame interpolation. Binaries can't show whether GameHub trained GSFG to imitate LSFG's output or took ideas from reading lsfg-vk. The host code still comes from the same /Users/me/Documents/GameScopeVK source tree, with a new gsfg_interpolator namespace.

Likely causes · untested

Why it may look worse

  1. A coarse motion map. Motion is worked out at a quarter of the motion resolution and stretched 4× on screen. Expect soft or haloed edges and trouble with thin objects and HUD text.
  2. A much smaller model. Half the channels, one refinement block instead of two, and no fine-level search: 3–4× fewer weights than 1.4.8.
  3. 8-bit internal state. Encoder features and each level's context are stored with 256 steps instead of 1.4.8's 16-bit. The old engine also used mostly 8-bit working images, so this alone probably isn't the main cause.
  4. "Quality" presets no longer pick a better model. There is only one model; Clear and Extreme only raise the resolution.
  5. Less range for fast motion. The pyramid now stops one level earlier.
  6. Errors multiply at 3× and 4×. One motion estimate is reused for every invented frame.
Action

What it means for BannerHub

  • Hold at 1.4.2. The API keeps serving firmware 1.4.2 (versionCode 32) to every client. Every surface was verified live on 2026-09-11, and the hold stays until it's lifted.
  • Our clients point at the deleted library. BannerHub (BhFrameGenWriter.java:110), BannerHub Lite (BhVulkanIcdWriter.java:61) and BannerHub v6 (BhGpuSpoofController.java:66) all default to libGameScopeVK.so. Serving 1.4.8+ as-is would leave frame gen pointing at nothing, or break Vulkan start-up, depending on the client.
  • GSFG turns itself off silently when X11 Present idle notifications can't be registered, or when the GPU lacks shaderFloat16 or storageBuffer16BitAccess.
  • If we ever want to judge it properly: run a side-by-side device test of 1.4.2 against 1.4.9 in the same game, with the client patched to use V2.
Plain-language reference

Glossary

Frame generation
Inventing extra frames between the real ones so motion looks smoother.
Optical flow / motion map
A picture-sized map saying where each spot moved between two frames.
Warp
Sliding a frame's pixels along the motion map.
Pyramid · level
Smaller and smaller copies of a frame. Search the tiny one first, then refine on bigger ones.
Search window (cost volume)
For each spot, how well it matches each nearby position in the other frame. 7×7 means 49 positions checked.
Weights · parameters
The learned numbers inside a neural network. More weights means more capacity for hard cases.
Channels
How many values the engine keeps for each spot on its internal maps.
Precision
How finely each value is stored. 8-bit has 256 steps; 16-bit float is far finer.
Pass (dispatch)
One GPU program run. More passes usually means more time per frame.
Shader · SPIR-V
The GPU programs, and the compiled form Vulkan loads.
Motion resolution
The size GSFG analyses frames at, as a percentage of the game's resolution.
Multiplier
Frames shown per real frame. 2× adds one; 4× adds three.
ICD
The Vulkan driver entry GameHub uses to slip frame gen in front of the real GPU driver.
LSFG · lsfg-vk
Lossless Scaling Frame Generation, and the open-source Linux project that runs it and named its stages.
