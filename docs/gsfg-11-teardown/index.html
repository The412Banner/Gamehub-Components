GSFG 1.1 Teardown

What GameHub's new frame-generation model is, how it is built, and whether it came from LSFG or another community project, recovered from the shipped binary.

Verdict

XiaoJi trained this model themselves. It is not LSFG, and it is not taken from any public project. GSFG 1.1 is a small learned optical-flow interpolator, about 10.1k parameters, with fp16 weights compiled into 36 Vulkan compute shaders. It was checked against LSFG 3.1, lsfg-vk, the old GameScopeVK engine, RIFE, IFRNet, FSR 3, RAFT and 30+ other models. It matched none of them in weights, kernel names or descriptor layouts. It is a from-scratch retrain by the same team and codebase that made GSFG 1.0.

This is the opposite of the pre-1.4.8 engine. The same test shows that GameScopeVK carried LSFG 3.1's actual trained weights: 44 of its 45 weight-bearing shaders matched one LSFG resource value for value. GSFG 1.1 matches nothing.

What byte-level analysis cannot rule out: a model trained to imitate another engine's output leaves no trace in its weights. XiaoJi's own benchmark data has a per-clip lsfg_check field, so LSFG 2.0 was in their evaluation pipeline. Nothing shows it was used as a training target.

Where it lives

Firmware 1.5.1 is newer than 2.0.0. GameHub orders firmware by versionCode, and 1.5.1 is vc 41 against 2.0.0's vc 40. Its sp_winemu_unified_resources.xml row is IMAGE_FS:id:1, md5 bb2ab51f…, state INSTALLED. Every file in the tree was hashed, and only one file changed.

The model is entirely inside libGameScopeV2.so. There is no separate weights file. A table in .data.rel.ro at 0x192be8 lists 36 entries of {name, SPIR-V pointer, size}. Those are the model kernels m00–m35. Three more unnamed modules (m36–m38) are BCn texture decoders, byte-identical to 1.4.9. The 1.4.9 tensor and pass tables are gone: the host now builds the graph in hand-written code.

The network

It is still an optical-flow interpolator with a cost volume, now much leaner. The design is closest to a compact PWC-Net / RAFT hybrid: flow is refined coarse to fine, and at each level the features are matched in a small window around the current estimate. Flow is bidirectional and anchored at the in-between time t, like RIFE. A learned 4-way selector plus a hand-built photometric rule then blends four warped candidates.

How it is built

  • Every learned block has the same shape: a 1×1 fusion layer, then depthwise 5×5 + pointwise, then depthwise 5×5 + (I+W) pointwise, then tiny heads. That is MobileNet/ConvNeXt style. The residual skip is folded into the second pointwise matrix: its diagonal sits at 0.96–1.18.
  • Activation: a leaky clamp to [0,1] with slope 0.01. Hidden tensors are stored as RGBA8, so the stored copy loses the leak.
  • Precision: all network maths is fp16 f16vec4. Softmax, warps and final synthesis run in fp32.
  • hc8 / hc16 are one model at two storage precisions. Their weights are byte-identical, and a host flag picks 8-bit or 16-bit correlation keys. The _decoded variant reproduces the 8-bit round trip exactly. So 8-bit quantisation was part of training.
  • Trained in PyTorch, then hand-exported. Pooling follows adaptive_avg_pool2d semantics and resampling is align_corners=False. Tensors use NCHW layouts. Each layer was then written out as GLSL with its constants baked in, and compiled with shaderc and stripped: 0 debug names, against 345 in 1.4.9.
  • Not a hypernetwork. Every weight is a compile-time constant, and there are no weight buffers anywhere.

The ±2 search window at the coarse level replaces 1.4.9's global search, which reached down to 1/512 resolution, and the new encoder is a single 580-parameter stage.

Host engine

It is still the same Vulkan ICD shim: it exports only the three vk_icd* symbols, loads the real driver, and presents through DRI3 pixmaps and xcb_present_pixmap. There is no JNI and no new environment variable. The app drives it through an 11-byte memory-mapped control file at $GAMESCOPE_CONTROL_PATH.

Adaptive multiplier

It starts at 1× and aims for ⌈target ÷ source⌉, capped at 6×.

  • Steps up: after two measurement windows (≥ 8 batches and ≥ 750 ms each) where GPU work is under 16.25 % of the source frame time and present wait is ≤ 10 %.
  • Steps down: above 21.25 %, or when the game's own frame rate drops more than 15 %.
  • Backoff: 2, 4, 8, 16, then 30 s.

Adaptive mode re-runs the flow network for every generated frame, because its timestamps fall unevenly.

Requirements and silent-off conditions

  • shaderFloat16 and VK_KHR_push_descriptor are both mandatory, with no descriptor-set fallback. Without them, backend creation fails and frames pass straight through.
  • If X11 Present IdleNotify can't be registered (it now tries a second xcb connection first), frame generation stays off.
  • The per-user ICD JSON still points at libGameScopeVK.so, which 1.5.1 no longer ships.
  • The Adreno 840 (vendor 0x5143 with "840" in the name) gets a special 16-bit "decoded" kernel variant.

Provenance

Four independent checks were run: identifier and string fingerprints, descriptor-layout signatures, SPIR-V structure, and weight matching. The weight matching compared exact fp16 runs, ±1-ulp runs, sign-flipped and scale-invariant runs, cross-correlation, and an order-free per-module containment test. Each test was calibrated on two known cases first. The old engine against LSFG was the positive control: the order-free test caught it at 100 % (12 of 19 tables). GSFG 1.4.9 was the negative control.

A GitHub code search for the distinctive names (hb_dwmix, hy_synth, hc16_update_pre, fast_ui_mask, gsfg_interpolator) found no public code. The only hits were generic words such as "pyramid".

A correction to the August record. Our September 11 teardown said LSFG has "zero learned weights". That was a parsing mistake: DXVK's DXBC translator stores the constants as integers, and the old extractor skipped them. Decoded properly, Lossless.dll holds about 29.8k trained weights. 44 of the old GameScopeVK's 45 weight-bearing shaders match an LSFG resource exactly after fp16 rounding, covering 97.6 % of its weights. So the old engine carried LSFG 3.1's real trained weights, not only its design. The earlier teardown has been corrected.

What XiaoJi says

XiaoJi launched an official page on 2026-09-29 (Last-Modified 14:09 GMT): gamehub.xiaoji.com/en/gsfg. It is linked from the GameHub homepage as "AI Frame Gen". It confirms the teardown in their own words:

  • GSFG = "GameSir Frame Gen". GameSir is XiaoJi's own brand.
  • "The model also reads a history frame and uses three consecutive frames to find UI regions that stay still…" This is the learned UI branch.
  • "The motion estimated for the previous pair of inputs is kept and reused for the next pair." This is the warm-start prior.
  • "…a second branch estimates small motion from zero" is the local branch. "A fusion network weights the two candidates" is the blend selector. "A first-pass image guides the upsampling" is hy_synth_guide.
  • "…network weights baked into the shaders in half precision."
  • Continuous t: 2×, 3×, 4×, 6× and fractional ratios (1.5×, 2.5×) from one model. Claimed cost on an Adreno 840 at 720p with 60 % motion resolution: 1.39 ms per frame; 6× costs 4.05 ms.

Not stated anywhere public: who trained it, the training data, any partner or open-source base, any licence or LSFG statement, and device requirements. The story that "the LSFG dev asked GameHub to take the old engine down" exists only as Reddit hearsay from 2026-09-12. GSFG 1.0 was widely panned on Reddit and Bilibili. There are no public reactions to 1.1 yet.

Open questions

  • Exact level resolutions, and whether the coarse level repeats over several octaves.
  • Which three feature maps feed the UI branch.
